# P11 operator data graph review

This is a read-only review of the pristine generated data, not acceptance of the operator implementation or the MathJax port.

The pinned TypeScript source is `.reference/MathJax-src/ts/core/MmlTree/OperatorDictionary.ts`, SHA-256 `9afac6e3a8f3b778247a5a678c529b9edddb8172850df7384511bf61dfbffd37`. The resolved package CJS is `tools/mathjax-bundle/node_modules/@mathjax/src/cjs/core/MmlTree/OperatorDictionary.js`, SHA-256 `db65e13a8f3c6290e711303d46cfb6f2fe8ec24e12c499bdf9b1bf4f42027ff8`; both agree with `docs/math-port/evidence/p11-source-lock.json`.

`tools/math-port/operator-data.cjs` validates the lock and package/source copy, requires only the OperatorDictionary module, traverses the four exported object roots, and asserts that every reachable ordinary object/array has its standard initial prototype. Its `--check` mode passed against the generated output and reports 129 reachable records and 1,252 operator entries. The generated native file is `src/math/core/mml_tree/operator_dictionary_data.cpp`; the oracle fixture is generated by `tools/math-port/operator-oracle.cjs` from that same CJS graph. Both generator `--check` commands passed; the fixture reports 9,840 assertions over four cases.

The graph's root fields map directly to the four root-owned accessors declared in `operator_dictionary.ixx`: `MO()`, `RANGES()`, `MMLSPACING()`, and `OPTABLE()`. The graph contains all 27 MO definitions, 50 range rows, eight spacing rows, and 137 prefix, 94 postfix, and 1,021 infix own keys. The 1,252 operator slots refer to 37 distinct initial definition arrays, preserving aliases rather than copying each table value. The traversal also includes each nested property object and each data array. The fixture recursively compares own keys, array/object tag, array length, every property value, and handle identity by comparing every edge against the same visited-node index.

The generated C++ constructs each JS array/object in a single `nodes` handle vector, initializes all fields, and then publishes the four roots. Its `PropertyArray` and `PropertyList` storage defaults model standard Array/Object prototypes implicitly: object records start with `objectPrototype=true`, arrays additionally set `array=true`; `PropertyList::get("__proto__")` resolves to the corresponding native builtin identity when no explicit prototype exists. The source generator separately asserts the upstream graph's prototype is `Object.prototype` for object records and `Array.prototype` for arrays. The fixture checks own graph fields and identities, but does not directly assert `__proto__` for every one of the 129 generated nodes; adding those per-node assertions would make the native side's initial-standard-prototype assumption explicit.

No LinebreakVisitor startup writes are baked into the pristine data. The generator's direct require resolves to OperatorDictionary only. A fresh Node probe showed the expected difference: before importing LinebreakVisitor, postfix fence properties such as `!`, `|`, and `}` lack `linebreakstyle`, and `OPTABLE.infix["\u2061"][3]` is null; after importing it, those fence property objects have `linebreakstyle: "after"`, and the apply entry is a cloned definition with `{linebreak: "nobreak"}`. The generated data file has no `linebreakstyle` or `nobreak` fields. This correctly leaves those runtime mutations to the visitor/startup layer.

The six source exports are represented across the data and host implementation: the graph contains `MO`, `RANGES`, `MMLSPACING`, and `OPTABLE`; `OPDEF` and `getRange` are implemented in `operator_dictionary.cpp`. I found no missing source export or initial data entry. This audit did not build native code or exercise the frozen assertions; root owns those checks and acceptance.
