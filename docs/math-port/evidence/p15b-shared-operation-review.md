# P15b shared TeX-atom/operator operation review

Read-only architecture review of the proposed single `adjustOperatorTeXclass(MmlNode&, MmlNode*)` operation. No implementation or acceptance is implied.

## Source behavior and fit

The proposed extraction is behaviorally compatible with the two pinned sources if the free function treats its `MmlNode&` argument as the original JavaScript `this` and keeps all existing virtual calls against that receiver. `MmlMo.adjustTeXclass` is implemented in the accepted native `src/math/core/mml_tree/mml_nodes/mo_classes.cpp`; it reads `texClass()` and `prevClass()`, may mutate `prev` through `setTexClass`, writes receiver state through `setPrevClass` / `setPrevLevel`, fetches receiver attributes, performs the ordered BIN-class adjustments and returns `this`. Those are all public virtual MML operations, so they do not require a concrete `MmlMo` cast. TeXAtom is deliberately not a subclass of MmlMo; calling the same operation with the TeXAtom object as receiver is the correct analogue of the upstream prototype method assignment.

The source identity fact is distinct from behavioral reuse: `TeXAtom.ts:104` assigns `TeXAtom.prototype.adjustTeXclass = MmlMo.prototype.adjustTeXclass`, so the two JavaScript prototype properties refer to the same function object. A shared native free-function body guarantees one algorithm and one evolving implementation, but C++ member functions on distinct classes do not acquire the same member-function-pointer identity merely by delegating to that helper. Current `FactoryClass` / `MmlClassInfo` infrastructure captures constructor and static metadata, not arbitrary prototype method objects. Unless the frozen product contract exposes method-function identity, document this as a native host adaptation: preserve call/effect/return equivalence through one operation, without claiming observable JS prototype identity. If a test later makes the function object identity observable, a shared callable identity representation would be a separate contract/interface prerequisite, not a reason to duplicate the algorithm.

## Module and call-frame risks

The dependency direction can remain acyclic: a new operation interface depends on `mml_node` and the already-root-owned `mo_host` utilities; `mo_classes.cpp` and future `tex_atom.cpp` import that operation. The operation itself must not import `MmlMo` or TeXAtom concrete interfaces. It can use `host::moAttributes` from `mo_host.ixx`, which validates the virtual `attributes()` result and does not depend on `MmlMo`.

Keep exactly one `TreeCallGuard` for the shared algorithm. The accepted method currently enters one guard at `MmlMo::adjustTeXclass`. Put that guard in the extracted operation and keep both class entry points as thin delegators without their own additional guard; an extra wrapper guard would consume another recursion-budget frame for the same source method call. This does not remove the existing distinct guard in `MmlMo::setTeXclass` before it calls `adjustTeXclass`.

The helper must not use `dynamic_cast<MmlMo&>` or operator-specific fields. Its existing algorithm uses only MML virtual state, raw `Property` class comparisons, `prev`, parent/child graph reads, and `moAttributes`; downcasting would break the intended TeXAtom receiver semantics. Preserve the current source body verbatim in order, especially strict `TEXCLASS.NONE` comparison, truthy autoOP short circuit and mutation, getter/setter timing, previous-level attribute read, each BIN condition, the parent walk, and its partial writes before a malformed/null-parent error. Do not refactor shared conditions while extracting; the extraction should be mechanically reviewable against the accepted body.

## TeXAtom initialization

The proposed TeXAtom class-specific phase is consistent with MathJax. Pinned `TeXAtom.ts:45` initializes its own `texclass` field to ORD; its constructor calls `super(...)`, then explicitly invokes `setProperty('texClass', this.texClass)` at line 81. The current root binding has the needed phase ordering (`class_binding.ixx:17–21`: adopt, bind constructor, `initializeMml`, then `initializeClassFields`). Therefore setting the TeXAtom field to ORD and writing the explicit property in its own `initializeClassFields` is a suitable class-specific approximation of field initialization followed by constructor body. Do not move the property write into generic `initializeMml` or `AbstractMmlBaseNode`, as that would alter unrelated node classes. Ensure this hook does not call the shared operator adjustment; only TeXAtom's later `setTeXclass` should call its shared `adjustTeXclass` operation.

There is an implementation detail to freeze for the phase: the inherited source `texClass` getter must read TeXAtom's own ORD state, and the explicit property write must use that virtual getter (source expression `this.texClass`) after field state is established. This keeps the serialized property synchronized with source behavior and remains distinct from the `MmlMo` `_texClass` field, which the accepted Mo contract says is not interchangeable with the inherited field.

## Regression obligations before implementation acceptance

The shared operation should have one differential suite that invokes the helper through both entry points with equivalent tree/property states and compares return identity, all raw class/level values, previous-node mutations, call-order traces, and errors/partial mutations against actual CJS. Required cases include each BIN-reclassification branch, strict `NONE` versus null/missing/other raw classes, autoOP true/false and class predicates, `prev` null and non-null, inherited scriptlevel absent/raw values, embellished and multi-level parent chains, last-child success and malformed parent failures, and dispatch through TeXAtom after its child has first been classified with null. Also verify that the algorithm body exists once and wrapper calls each enter one shared-operation guard. A separate method-identity witness is only relevant if the native boundary elects to model JavaScript prototype function identity; current MML interfaces do not expose that object.

No source, interface, test, build, or contract files were changed. The review identifies no dependency cycle that blocks the proposal, subject to the function-identity adaptation and guard ownership above; root acceptance remains outstanding.
