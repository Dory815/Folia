## Finding

There is reusable C++ Irregexp source, including a real interpreter path, but neither V8's internal engine nor Mozilla's imported copy is a standalone regular-expression library. V8's API is coupled to V8's internal `Isolate`, `Zone`, handle, string, flag, allocation, and assembler types. Mozilla has already isolated and imported much of the source, but its API and shims are coupled to SpiderMonkey types, memory management, JIT infrastructure, and its own patches. A native-only matcher therefore looks technically possible as a substantial extraction/adaptation, but the primary sources do not establish a small, supported, stable, drop-in API. Exact behavior against the project's Node 24.13.0 oracle would also require pinning the matching V8 source and Unicode data, not merely taking current Irregexp.

The current differential experiment is strong evidence against choosing a generic “close enough” regex implementation: the root-reported `regress` candidate still differs from Node v24.13.0 in 1,964 of 119,218 observations. Patterns supplied through `setOptions` are reachable, so the required semantics cannot be inferred from the default MathJax regex set alone. This audit does not recommend replacing that candidate with Irregexp; it records what extraction would entail.

## Semantics and data obligations

Irregexp is designed for ECMAScript regex syntax and supports the relevant language-level constructs through its parser/compiler and interpreter/JIT paths: captures and capture registers, backreferences, lookahead/lookbehind, Unicode-aware matching, and zero-width assertions. The `/v` mode is not just a flag alias: ECMAScript adds nested character-class set operations and properties of strings such as emoji sequences. The `u` and `v` modes are mutually exclusive. V8 documents these features in its [Unicode sets and properties-of-strings article](https://v8.dev/features/regexp-v-flag). Exact syntax and edge behavior still depend on the pinned source and flags.

Irregexp consumes V8 strings, including one-byte and UTF-16 representations. A native bridge for a source-compatible matcher needs to retain UTF-16 code-unit indexing, including isolated surrogate code units, because JS `RegExp` match indices and `lastIndex` are code-unit positions. The source interface is not a public `std::u16string_view` API; adapting V8 string/handle types to such an interface is engineering work. Capture ranges should be checked against the JS oracle in UTF-16 units, including zero-length captures and unmatched groups.

The matcher/compiler is only one part of `RegExp` behavior. A native host still needs constructor validation and error mapping, source/flag normalization, global and sticky `lastIndex` read/write behavior, `exec`/`test` result protocol, named groups and `d` indices, and JS property/coercion semantics at the call sites. `g`/`y` behavior is stateful across calls; it cannot be modeled as a pure `matches(pattern,input)` function. This division is an inference from ECMAScript's observable RegExp object protocol and V8's internal compile/execute API; the linked internal API does not promise those semantics as an independent package.

Unicode behavior is version-bound. The project's comparison target is the installed Node v24.13.0 runtime, which reports Unicode 16.0 and ICU 77.1 in the existing generated case-data provenance. V8 compiler source has `V8_INTL_SUPPORT` branches that use ICU Unicode sets for special case folding; therefore ICU-enabled versus non-ICU builds are not safely assumed equivalent for Unicode ignore-case. Property escapes, string properties under `/v`, case folding, aliases and newly assigned code points can change with Unicode data. A newer Mozilla vendored revision or current V8 main is not evidence of exact Node 24.13 parity. An extraction would need an explicit policy for the exact source revision and Unicode/ICU payload, and tests that pin both.

## Build and execution boundary

V8's source describes two execution products: bytecode and native code. Its interpreter is a C++ bytecode interpreter, so disabling JIT does not remove the interpreter path. It does not remove dependencies on V8's bytecode representation, allocator/Zone, string/regexp flags, isolate plumbing, stack checks, and internal utility types. The native path uses architecture-specific macro assemblers and platform code generation. V8's [tier-up description](https://v8.dev/blog/regexp-tier-up) confirms that interpreter and native-code execution are distinct tiers. A regexp-only interpreter extraction could avoid shipping a JS evaluator and architecture-specific JIT, but would still require adapting or replacing internal runtime facilities while preserving exact parser, bytecode, Unicode, error and matching semantics.

Irregexp uses backtracking and can take exponential time on adversarial pattern/input pairs. V8's separately described non-backtracking engine is an additional restricted engine with exclusions such as backreferences and lookarounds; it is not a drop-in way to bound execution while retaining all ECMAScript patterns. That distinction matters because unrestricted patterns are reachable via `setOptions`. See V8's [non-backtracking engine description](https://v8.dev/blog/non-backtracking-regexp). This source documents a tradeoff, not a recommendation to enable that engine.

Mozilla's imported source list is useful evidence of the likely maintenance shape: parser, compiler, bytecode generator/interpreter, bytecode utilities, regexp API/shim, and Unicode shim are separate pieces, with additional architecture/JIT files and conditional Intl integration. It is not evidence that those modules compile standalone. Their SpiderMonkey API and JIT/allocator dependencies remain visible in the interface and shim sources. Inference: using Mozilla's maintained import as a starting point may reduce source discovery and license bookkeeping compared with extracting directly from V8, but adapting it to Folia would still be a port, and the Mozilla import revision may not match the Node oracle revision.

The V8 and Mozilla sources are redistributable under permissive BSD-style terms for the Irregexp code, subject to retaining copyright/license notices. The Mozilla glue has its own license and all copied files and dependencies would need individual notice review. This is a source-level license observation, not legal advice or a full dependency-license audit.

## Feasibility judgment and unresolved decisions

Evidence supports the following bounded judgment: an interpreter-only Irregexp integration without QuickJS or a JavaScript VM appears feasible in principle, but the inspected sources do not offer a ready-made VM-free matcher API. It would require selecting and pinning a source snapshot, adapting core allocation/string/flag/error interfaces, deciding how to preserve Node's Unicode 16.0/ICU 77.1 behavior, keeping all required ECMAScript features (including `/v`, backreferences and lookbehind), and continuously validating the bridge against Node v24.13.0. The runtime would remain regex-only; this finding does not require an evaluator or broader JS engine.

Before implementation, root must decide among: (a) maintain an Irregexp extraction/adaptation; (b) use another native engine and accept/close its observable divergences; or (c) keep investigating candidate sources. This audit does not choose. A narrower default-pattern-only engine would conflict with the reachable `setOptions` input surface described by the task.

## Limits of this audit

No V8 or Mozilla source tree was cloned or modified. No build or performance test was run. Source references above establish architecture and dependencies; they do not establish standalone buildability, matching parity, performance, security bounds, or the exact effort to extract. The `regress` mismatch count is a root-provided current experiment result, not independently rerun here. The Node tag's version header verifies the V8 version, but the exact source SHA for a prospective extract remains unselected and unrecorded. Mozilla references in this audit are deliberately labeled current and unpinned; their upstream imported-V8 revision must not be confused with a Mozilla changeset.
