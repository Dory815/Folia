## `inheritAttributesFrom`

Source order is significant (`MmlNode.ts:883–897`). It first reads `node.attributes` once and stores that object. From that same handle it reads `displaystyle`, then `scriptlevel`; next it calls `isSet('mathsize')`, and only if true reads `mathsize` to construct a fresh inherited-attribute object containing a fresh `['math', value]` pair. It then reads `node.getProperty('texprimestyle')`, applies JavaScript `|| false`, and finally invokes the receiver's virtual `setInheritedAttributes(defaults, display, scriptlevel, prime)`.

Consequences: `attributes.get(...)` values are passed through without boolean/number coercion. Prime uses logical OR with `false`, not `Boolean(...)`: falsey values become the boolean `false`, while truthy strings, objects, arrays, and other values pass through unchanged despite the TypeScript assertion. `isSet` and the conditional `get(mathsize)` are distinct calls and may observe mutations. The node property read occurs after all attribute reads. If an accessor/callback throws, no later read or receiver call occurs. A missing/invalid source node fails at the first `node.attributes` access; null attributes fail at `.get('displaystyle')`. The actual inherited setter may apply its own JS default arguments only when a passed value is `undefined`.

Native `AbstractMmlNode::inheritAttributesFrom(NodeValue)` is an explicit `Unimplemented` stub at `src/math/core/mml_tree/mml_node.cpp:536–539`; its declaration is `NodeValue`-tagged at `mml_node.ixx:80,140`. The empty-node implementation at `mml_empty.cpp:45–48` is also still an `Unimplemented` stub, although upstream `AbstractMmlEmptyNode.inheritAttributesFrom` is intentionally a no-op (`MmlNode.ts:1415–1418`, CJS 1000–1002). `setInheritedAttributes` is dispatched through the existing virtual API; do not replace that call with a direct base implementation.

## `verifyTree`, `verifyAttributes`, and `verifyChildren`

`AbstractMmlNode.verifyTree` (`MmlNode.ts:906–927`) has a parameter default of `null`, and immediately returns only for `options === null`. Otherwise it calls virtual `verifyAttributes(options)` first, then reads `this.arity`, then reads `options['checkArity']`. If enabled, it checks `arity >= 0`, `arity !== Infinity`, and the child count condition; source property reads are not cached across the boolean expression. On mismatch it calls `mError` with the message assembled from the current `this.kind`, the same options object, and `short=true`. Regardless of whether that call replaced the node or returned early, it then calls virtual `verifyChildren(options)` on the original receiver.

Thus `null` is a deliberate no-op. At this base method's call boundary, an `undefined` argument triggers the default parameter and is likewise converted to `null` before the body, so the base method also no-ops. Overrides can still observe the original argument before/after they call `super`: for example, an override with no default may receive `undefined`, and a derived method may pass that value to `mError` after the base call. A non-null primitive/object is not prevalidated: normal JS property access applies. The options object identity is forwarded unchanged to every verification and error callback. Errors thrown from attribute checking or `mError` prevent later arity/children work; an error replacement does not itself short-circuit the original method.

`verifyAttributes` (`934–967`) has two independently evaluated blocks. For `options.checkAttributes` truthy, it captures `this.attributes` once, gets the explicit-name list, and walks that list. Each name is accepted when it starts with `data-`, has a defined default, or matches `class|style|id|href|xlink:href`; otherwise it is accumulated. If any are bad, the error message reads `this.kind` at that later point and calls `mError` with the original options. It then separately reads `options.checkMathvariants`; if truthy, it re-reads `this.attributes`, reads explicit `mathvariant`, and, if truthy and absent from the shared `MATHVARIANTS` set and `ignore-variant` is falsey, calls `mError(..., true)`. The second block still runs after the first error callback unless it throws. Attribute names are iterated from the returned name array; callbacks can mutate the receiver/options between phases.

`verifyChildren` (`973–976`) is a JavaScript `for...of` over `this.childNodes`. The iterator captures the array object when iteration starts, but indexed values and array length remain live as the loop advances. For each yielded value, it calls that value's virtual `verifyTree(options)` with the same options identity. Rebinding the receiver's `childNodes` during a child callback does not change the captured iteration array; changing that captured array's length or slots affects subsequent iterations. A null/non-iterable child collection or non-callable child method fails at the actual iteration/member call. Abrupt completion performs iterator closing before rethrow.

Native `AbstractMmlNode::verifyTree` and `verifyChildren` are `Unimplemented` stubs (`mml_node.cpp:541–544,577–580`). The virtual hooks are declared at `mml_node.ixx:159–160`. `verifyAttributes` already has a body (`mml_node.cpp:546–575`), but this audit has not established its complete observable parity for accessor-driven/native-binding cases. Native `std::optional<PropertyList>` at `mml_node.ixx:81,141,223` and `ErrorOptions` do not visibly encode every JS argument state: source `null` and an omitted/`undefined` argument both no-op in the base method but are distinct values observable by overrides/callbacks; a `PropertyList` value also cannot represent arbitrary primitive options. Any later contract needs to state its supported typed domain rather than silently treating all states as equivalent.

There are source overrides whose ordering matters beyond the base methods:

* `MmlMath.verifyTree` calls `super.verifyTree(options)` and then checks raw `this.parent`; if truthy, it calls `mError('Improper nesting of math tags', options, true)` (`math.ts:126–132`). The base call can already replace this node; the subclass still proceeds and reads parent afterward.
* `MmlMprescripts.verifyTree` and `MmlNone.verifyTree` call the base first, then read parent, then (if truthy and the parent kind is wrong) read `this.kind` and invoke `mError` with `short=true` (`mmultiscripts.ts:177–186,221–230`).
* `HtmlNode.verifyTree` does not call the base. It reads parent and, if truthy, reads `parent.isToken`; on false it calls `mError('HTML can only be a child of a token element', options, true)` and returns (`HtmlNode.ts:96–102`).
* `MmlMmultiscripts.verifyChildren` is a separate override (`mmultiscripts.ts:108–141`): it uses a live indexed loop on `this.childNodes` (not for-of), captures `fix = options['fixMmultiscripts']` once, and calls `child.isKind('mprescripts')` for each current slot. A second marker triggers that child's `mError`; the first records `prescripts=true`, and if at an even index with falsey captured `fix`, calls the container's `mError`. After the loop it re-reads current child-array length and may call another `mError`, then calls `super.verifyChildren(options)`. Error callbacks can change the current array, later branch state, or descendants; do not normalize this to one snapshot/one error.

The empty-node source overrides are intentionally different: `AbstractMmlEmptyNode.verifyTree` is no-op and `mError` returns `null` (`MmlNode.ts:1417–1427`); native equivalents are `mml_empty.cpp:49–50` and already express those outcomes.

## `mError`

`MmlNode.ts:987–1022` makes the following ordered mutations and re-reads:

1. If `short` is `undefined`, default it to `false`. Evaluate `this.parent && this.parent.isKind('merror')`: this is two separate `parent` property reads when the first is truthy. If the second read's `isKind` is true, return `null` without reading `options` or mutating anything.
2. Call `this.factory.create('merror')`; then read the new node's `attributes` and set `data-mjx-message` to the supplied message.
3. Read `options.fullErrors`; if truthy or `short` is truthy, create `mtext`, create `text`, then read `options.fullErrors` again to choose `message` versus the current `this.kind` for `text.setText`. Append text to mtext and mtext to merror. Re-read `this.parent` and call its `replaceChild(merror, this)`. After replacement, read `options.fullErrors` a third time; if falsey, set `title=message` on the merror attributes.
4. Otherwise, re-read `this.parent` and replace this node first, then append the original node under merror.
5. Return the created merror.

This deliberately does not use the `Parent()` accessor that skips nodes marked `notParent`: it reads the raw `parent` field. The guard's first parent and the replacement's later parent are separate reads. Factory/attribute/append/replace callbacks can change parent, options, or kind between those steps. The options reads are repeated rather than cached. Partial changes survive failures: for example, factory creation and `data-mjx-message` assignment precede a failure reading `options.fullErrors`; the full-error subtree is attached before the replacement parent access; in the ordinary branch replacement is attempted before appending the original node. A top-level node with no parent therefore reaches a nullish `.replaceChild` failure after the earlier branch-specific mutations. If already inside `merror`, the early null return precedes all these effects.

Current native `AbstractMmlNode::mError` is an `Unimplemented` stub (`mml_node.cpp:582–585`). The public native return is `MmlNode*` (`mml_node.ixx:82,142,224`), which can express a normal node or null return, while options are wrapped in `ErrorOptions` (`mml_node.ixx:15–28`) and the factory exposes `create(kind,args)` (`tree/factory_types.ixx:42–51`). The wrapper distinguishes an absent options handle from a `PropertyList`, but does not itself represent arbitrary JS primitive option values. Its value accessor returns an optional shallow handle; `get()` throws for null. No native body currently demonstrates source-equivalent repeated reads of `fullErrors`, raw-parent re-reads, factory call ordering, or partial mutations.

## Current native frontier

`AbstractMmlNode::inheritAttributesFrom`, `verifyTree`, `verifyChildren`, and `mError` remain explicit stubs in `mml_node.cpp`. `MmlMath.verifyTree`, `HtmlNode.verifyTree`, `MmlMmultiscripts.verifyChildren`, `MmlMprescripts.verifyTree`, and `MmlNone.verifyTree` also remain stubs in their respective native files. The base `verifyAttributes` body exists, and empty-node `verifyTree`/`mError` are no-op/null. This report identifies the source obligations and call relationships; it does not authorize or propose a replacement API.
