## Ordered behavior of inheritance normalization

The base child is accessed and called first (`71–76`): the implementation reads `this.childNodes[0]` and invokes `setInheritedAttributes(attributes, display, level, prime)` before any marker traversal. An absent/null base therefore fails at that receiver; later array normalization is not reached. The source does not snapshot `childNodes` into a local array. Every loop condition, indexed read, splice, and final length/index operation goes through the current `this.childNodes` property, so a child callback that replaces the property retargets later source accesses; in-place edits to the same array are also live.

At `78–95`, the loop starts at child index 1 with a local non-marker count `n=0`. The loop reads current `childNodes.length` each iteration and the child at the current index. `isKind('mprescripts')` is called on every visited child. Only the first marker switches `prescripts` to true. If that marker is at an even index, the factory creates kind `none`, `splice(i,0,none)` inserts it into the exact current array object, `none.parent=this` is then assigned, and local `i` is incremented; the `for` increment advances once more, skipping the marker just processed. This preserves the input array identity and changes its contents. The marker does not increment `n`; each other visited child receives inheritance with the exact same `attributes` object, display `false`, JavaScript `level + 1`, and `prime || (n % 2 === 0)`, then increments `n`. Because JS `||` returns an operand, a truthy non-boolean `prime` is passed through unchanged. The loop's mutations and child callbacks can affect later live indices and length.

After the loop (`96–104`), parity is recomputed from the current `this.childNodes.length` and the local `prescripts` flag. On a mismatch the code evaluates `this.factory.create('none')` as the argument to `appendChild`, then reads `this.childNodes.length` again, fetches its current last child, and calls inheritance on that result with attributes, `false`, `level + 1`, and the original `prime` (not the alternating `primestyle`). Thus factory creation, append, and the final lookup are distinct ordered steps; callbacks can expose changed receiver/array state between them. `appendChild` has the ordinary tree implementation's parent assignment behavior.

Important edge semantics for a future frozen contract: `level + 1` is JS primitive addition, not necessarily numeric addition; parity uses JS remainder/coercion rules; truthiness and `||` preserve raw operand values; marker tests are virtual calls; and child-array edits, parent writes, and inheritance calls are observable. The inherited method's declared `display:boolean`, `level:number`, `prime:boolean` do not remove runtime JS coercion/alias semantics.

## Ordered behavior of validation

`verifyChildren(options)` (`112–142`) reads `options['fixMmultiscripts']` once into local `fix` before scanning; the subsequent conditions use JS truthiness of that captured value even if an error callback mutates options. Its `for` condition rereads `this.childNodes.length`; each iteration rereads `this.childNodes[i]` and calls `isKind`. A repeated marker invokes that marker's `mError` with a message assembled in order from `child.kind`, the fixed text, and `this.kind`, then the same options object and `true`; if that call returns, scanning continues. The first marker sets `prescripts=true`; an even marker index causes the node's own `mError` only when `!fix`. After the loop, current child length is reread for total parity; mismatch similarly calls `mError` only when `!fix`. Finally `super.verifyChildren(options)` is called regardless of whether earlier non-short errors returned. The base implementation walks the children and calls each child's `verifyTree(options)`, so marker/none parent checks occur in this later phase. A thrown error interrupts the remaining sequence naturally.

The superclass `AbstractMmlNode.verifyTree` (`MmlNode.ts:906–927`) has a default `options=null`, returns immediately for null, otherwise runs `verifyAttributes`, optional arity validation controlled by `checkArity`, then virtual `verifyChildren`. `mError` (`MmlNode.ts:985–1016`) can create and attach `merror`/`mtext`/`text` nodes depending on options; the native implementation exists in `mml_node.cpp`. Therefore a future `verifyChildren` packet depends on the exact typed error-options/null behavior, factory bindings, dynamic child kind calls, and superclass dispatch—not only its parity arithmetic.

## Parent, child-array, and factory model

In JS, `Tree/Node.ts:166–177` initializes each normal node with a parent field and a mutable `N[]` child array; `Node.ts:208–244` implements append/splice-like child operations and parent links. The multiscript source directly mutates the array with `splice` and directly assigns `none.parent` rather than using an abstract immutable tree representation. The factory call is `this.factory.create('none')` at `mmultiscripts.ts:84` or `:97`; source factory resolution determines the concrete product class and constructor state.

The accepted native tree boundary in `src/math/core/tree/node_types.ixx` uses `Product* parent` and `shared_ptr<vector<Product*>> childNodes`; generic `appendChild` sets `parent`, and `setChildren` creates a new vector and appends elements (`node.ixx:64–88`). That is enough storage to represent pointer children, parent links, and in-place vector insertion, but no native `MmlMmultiscripts`, `MmlMprescripts`, or `MmlNone` declaration or implementation is currently present. The module declarations in `mml_node.ixx` and current `msubsup.ixx/.cpp` expose only `MmlMsubsup`, `MmlMsub`, and `MmlMsup` for this family. The current `tests/math/reference_script.cpp` fixture registers those script types and `munderover` types but not the three classes in this source.

`PropertyArray`/JS array storage now carries presence and alias identity for ordinary option arrays, but this MML `childNodes` contract is separately typed as a vector of raw node pointers. An eventual packet must define whether null slots stand in for JS `null` versus holes/undefined, preserve the actual child-array handle during `splice`, and distinguish operations that keep the current array from operations that replace it. No accepted multiscript packet/oracle was found in the current native boundary or `tests/math` references. Do not treat the existing `msubsup` conformance fixture as evidence for marker normalization, verification diagnostics, or the `fixMmultiscripts` option.

## Concrete gaps for the next contract freeze

1. Three concrete kinds and their factory bindings are absent: `mmultiscripts`, `mprescripts`, and `none`. The base type and generic factory can express the needed family, but no accepted registrations or defaults bindings exist.
2. No accepted native contract currently specifies marker positions, repeated marker handling, independent pre/post parity, or the distinction between validation and inheritance-time normalization. The source has two different paths: verification reports errors; inheritance inserts placeholders.
3. The native tree's vector has no sparse array holes and `nullptr` is not a distinct representation for JS null, undefined, or a missing array slot. The three source members assume array reads and direct indexed child calls; malformed inputs need explicit host behavior rather than C++ unchecked access.
4. The current msubsup hook snapshots its shared child vector once and has fixed base/sub/sup accesses; the multiscript source instead repeatedly dereferences `this.childNodes` and performs a direct `splice`. Reusing the msubsup implementation strategy would change replacement/callback behavior.
5. `fixMmultiscripts` is a truthy option that suppresses selected `mError` calls but does not suppress superclass child verification and does not perform fixes itself. Its read is captured before the loop. This branch needs dedicated frozen cases rather than inheriting `fixMtables` or generic arity expectations.
6. The source default `arity=1` means generic `checkArity` permits any child count at least one only insofar as the base verifier's special arity rule treats 1 as a minimum; the separate parity verifier covers the remaining shape. The native generic verifier currently uses the same one-child special case, but the new kind's exact arity binding and error order remain untested.
7. Error behavior depends on `mError` returning versus throwing, error-node attachment, and later superclass verification. No current fixture establishes the exact `mError` count, message, options identity, short-error flag, or partial mutations for malformed multiscripts.

This audit does not propose replacement interfaces or claim native support. Root must freeze the class, factory, array-mutation, options/error, and oracle boundaries before implementation is assigned.
