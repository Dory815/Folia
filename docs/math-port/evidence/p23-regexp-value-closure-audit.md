# P23 — RegExp value and operation closure audit

This is a read-only closure audit for the pinned MathJax 4.1.3 profile. It does not choose or specify a native RegExp API, and it does not accept the ignored Rust candidate as a compatible engine. No source behavior is waived by the current native service boundary.

## Where RegExp values enter and how they travel

The locked `entry.cjs` (SHA-256 `a5a03eed8a10872b9b435b9e602523a08a9f574e21cc5636e8377f0222811ac9`, lines 54–66) initializes TeX with the selected package list. `BaseConfiguration.ts` (SHA-256 `578d2c6b03f2f3e902476a0b73a5323b12262215fcbdc831a1135c1d9c1737ad`, lines 162–171, 222–228) supplies RegExp defaults for `numberPattern`, `initialDigit`, `identifierPattern`, and `initialLetter`. During the one-time CONFIG callback it captures `initialDigit` and `initialLetter` into two `RegExpMap` instances. The default patterns are non-global/non-sticky, but their object is still the stored source value.

The enabled `setoptions` command is a second, input-reachable producer. `ParseUtil.readKeyval` (`ParseUtil.ts`, SHA-256 `b43646071997f88f27df51610c7972a8cb5791ea76194e7318d17d1a2f81f76a`, lines 104–120) converts the exact spellings `true` and `false` into booleans; a bare key also becomes `true`, while other values stay strings. `SetOptionsUtil.filterValue` (`SetOptionsConfiguration.ts`, SHA-256 `ccaa243137c68208e7f442013aa5dc6cc04b735ac3e0ca099ea8f30be557790d`, lines 128–139) returns non-string values unchanged, compiles strings shaped as `/pattern/flags` with flags drawn from `dgimsuvy`, and returns all other strings unchanged. `SetOptions` assigns the result directly to the live option object at lines 148–158. The profile's option filter permits ordinary `tex` options; it only denies the listed keys at lines 204–219. Thus TeX can replace `numberPattern` or `identifierPattern` with a compiled RegExp, `true`/`false`, or an arbitrary string. `null` written in TeX is the string `"null"`, not JavaScript null; this parser has no null literal. A real null can enter only through external option/configuration mutation, outside the locked `entry.cjs` input syntax.

The consumers make the distinction material. `ParseMethods.digit` (SHA-256 `1cdc4c6828078cd40863269864cdd6b7e5d22024e2ed36f4eeafb673781a5a70`, lines 80–90) fetches `parser.configuration.options['numberPattern']` for each digit and calls `String.match` with that current value. `BaseMethods.MathFont` (SHA-256 `7336240c8f9c5037f9fdcd5a84ea079312854f1ef3f406aeb5a8b6a8ff765cda`, lines 414–431) reads `identifierPattern` when creating the nested parser; `ParseMethods.variable` then uses that environment value in `String.match` at lines 42–51. When these values are strings or booleans, JavaScript String-match semantics coerce them as patterns; they are not rejected merely because the original option was a RegExp. In contrast, changing `initialDigit` or `initialLetter` with `\setOptions` changes only the option property after CONFIG: the already-constructed `RegExpMap` still retains its original RegExp reference. `BaseConfiguration` also copies truthy legacy `digits` into `numberPattern` only during CONFIG (lines 164–167), so a later `digits` assignment does not repeat that copy.

At source level, `RegExpMap` stores the exact constructor value in `_regExp` and calls `_regExp.test(token)` without resetting it (`TokenMap.ts`, SHA-256 `0209895b13569008b2129b61c88050e7c70e70ce9477d234b9a6e303a86a738e`, lines 147–175). `lookup` calls `contains` again. P22b preserves that double-test and live call order, but its `RegExpContext` is a separate identity-bearing service: the native interface exposes only `test(const Property&)`, and `RegExpMap` stores `RegExpRef` separately from the source option/property graph (`token_map.ixx`, SHA-256 `ee5e877439dff33fbd64dec62672f93d79114f50dde95f06ebf6843e325906e1`, lines 16–21, 40–52; `token_map.cpp`, SHA-256 `0f8f4e130b36f65a5045b5574b9400835910e8bc3679eabb7584c8aa44a9c249`, lines 167–179). This is enough to test map dispatch in controlled fixtures, not enough to represent a JS RegExp value or accept the regex engine.

The shared `Property::Value` (`property.ixx`, SHA-256 `1c2dc6779ba822b1e07aff1345390e0cd62d0222458b4784483d2cdd86e12a3a`, lines 23–40) admits Missing, null, scalars, strings, builtins, property-storage objects, and FunctionRef, but no RegExp object/ref alternative. `property_host` handles these scalar/object shapes; callable property evaluation is explicitly unbound, and there is no regex property lookup or `lastIndex` binding (`property_host.ixx`, SHA-256 `df79652431896f37073fbdef4bcd668a09893c8547c6369f63fb21e492c144ea`, lines 123–191). A separate `RegExpRef` cannot preserve identity when the same regex is stored/read as an ordinary option Property, nor can Property distinguish a regex from an arbitrary object. The current native boundary therefore cannot model all reachable value replacement and getter/receiver behavior by composing the accepted Property and RegExpContext types.

## Required operation surface in the pinned source closure

The P19c AST inventory covered all 246 source files in the fixed 38-package closure at commit `fb987178c2d279a99b0db5ea02e751691703955e`: 227 regex literals, 17 RegExp constructor/call sites, and 216 regex-valued method sites. Its operation counts are `RegExp.test` 1, `RegExp.exec` 5, `String.match` 107, `String.replace` 71, and `String.split` 32; no regex-valued `String.search` or `replaceAll` site was found. These are source-closure counts, not a claim that every call executes for each `render(tex)` invocation.

The directly demonstrated parser paths are `RegExpMap.test` and the live `String.match` option consumers above. The wider enabled closure includes:

- `FindTeX.ts` (SHA-256 `65355d94cac0c1e8a790313c52e231212733b5a98d6f6697c2c7864812a72944`): builds a global start regex at lines 135–140, executes end patterns at 187–197 and start patterns at 221–255, and explicitly writes/observes `lastIndex`. The locked `entry.cjs` calls `document.convert`, not the DOM `findMath` scan; this is a real package dependency path but not established as a direct formula-render call.
- `MhchemConfiguration.ts` (SHA-256 `bacc438afa26698e9e7d8ad6e4a6094eefa12f0d265c4384d60c0dbb474c4ace`): six global regex literals feed `String.replace`; one replacement entry is a callback, so capture arguments and callback result rules are observable. The package is enabled, while the imported mhchem parser itself is outside the 246-file TypeScript inventory.
- `mo.ts` (SHA-256 `2082cd372a4c21fa46c67ab3972b51bcc950f711dd3369cbb2bd7ced62c2f605`): static regexes classify operator names, pseudo-scripts, primes, and accents. This does not make arbitrary flag behavior optional for the separate dynamic `setOptions` consumers.

The profile therefore requires regex construction/validation for TeX-supplied `/pattern/flags`, test with stateful object semantics when a global/sticky RegExp is supplied at construction, and the JS behavior of match/exec/replace/split where those source call sites are reachable. `lastIndex` is directly read/written at the three `FindTeX` sites in P19c's inventory; `RegExpMap.test` also implicitly consumes/mutates it when the stored object has `g` or `y`. No source code directly reads `.flags` or `.source`, but flags control construction and operation behavior. There is no positive source closure demand for `String.search` from the audited 246 files; that observation does not grant a reduced generic RegExp contract.

## UTF-16 candidate boundary and remaining evidence

The ignored `regress` 0.12.0 candidate is a pattern matcher with explicit UTF-16 input paths, not a JavaScript RegExp object host. Its current P21d files are an isolated copy; source `api.rs` is byte-identical to `.reference/regress` (`b748e71e56e40c46108b86842dc0face872ff9b0d4f36f5612aa0f61731c424a`). `Regex::with_flags` accepts a Rust `&str`; `Regex::from_unicode` accepts a `u32` iterator (candidate `api.rs`, lines 420–444). `find_from_utf16` and `find_from_ucs2` take a `&[u16]` plus a numeric start offset (lines 549–580). `Utf16Input` preserves UTF-16 unit positions and combines a valid high/low pair into a scalar during traversal, while unmatched surrogates remain units (`indexing.rs`, SHA-256 `8df75d23395147e16a06112aba619d8305eba6a0455046c2fe3291ed303ab5f4`, lines 855–969); `Ucs2Input` traverses each unit independently (lines 1123 onward). Candidate `Match` exposes a whole-match range, optional capture ranges and named-group lookup (`api.rs`, lines 155–225). These are useful matcher-level offsets and captures, but not a JS match-result object.

The candidate `Flags` type has booleans for `i,m,s,u,v`. Its constructor explicitly says `g` is unsupported and silently ignores other unsupported flags (`api.rs`, lines 18–86); it has no `d` indices, global/sticky state, regex object identity, mutable `lastIndex`, getter, or JS constructor/property protocol. `find_from_utf16` accepts a caller-chosen start number but does not own or mutate that number as a RegExp property. It has no `exec`, `test`, `match`, or `split` protocol object. Rust-side `replace`/`replace_all` and callback variants exist (`api.rs`, lines 583 onward), but their documented replacement-string/callback API is not the ECMAScript String/RegExp result protocol (for example, it does not produce the JS arrays and properties returned by match/exec or the captured-field array returned by split). Pattern `&str` also cannot directly carry lone UTF-16 surrogates; `from_unicode` is a separate codepoint iterator, not a JS string/object bridge.

The P21d source replay is evidence of progress and unresolved mismatches, not engine acceptance. Root's reviewed six-corpus replay records 227,684/227,712 equal for the v-casefold corpus, 28 remaining ordinary `ui` class-control cases, and zero regressions; the full result is in `p21d-v-casefold-root-review.md` (source fixture SHA-256 `0d65e4dcf82471c630fcea1f370e444af451c86b4b9cecb886ff80cbe87db063`). Separate inventories still report 293 original cases, 18 legacy braced-escape cases, and 144 Unicode16 property alias cases. P21d also reports the unchanged upstream UTF-16 suite at 495 passed / 56 failed / 1 ignored. These matcher discrepancies are independent from the unimplemented RegExp object state and JS operation/result semantics above; a passing controlled `test` service cannot bridge them.

## Boundary summary for the next contract freeze

| Concern | Existing accepted native representation | Closure still visible in source |
|---|---|---|
| Regex as option value | `Property` handles bool/string/null/object; `RegExpRef` is separate | One value identity must travel through config/property operations and may be replaced by bool/string or externally null; current types do not put RegExp in Property. |
| Regex matching in RegExpMap | Abstract `RegExpContext::test(Property)` called twice through contains/lookup | Actual constructor, flags, source object state, global/sticky `lastIndex`, identity, failures, and property getter order are unbound. |
| Regex start/range | Candidate accepts explicit start and returns capture ranges; UTF-16 input offsets are code units | Stateful exec/test and reset/update of the same object `lastIndex`; JS result arrays/indices/groups and coercions. |
| String regex operations | Candidate provides matcher and separate Rust replacement helpers | ECMAScript `String.match`, `exec`, `String.split` captures, replace tokens/callback protocol; no audited `String.search` call site. |
| Invalid dynamic values | TeX source can produce boolean and ordinary string; slash form constructs RegExp or throws | Exact `String.match` coercion for boolean/string, and externally supplied null/object/accessor cases if included in the final host profile. |

No source, API, test, fixture, build, or commit was changed; this audit did not run any build, test, or experiment. The ignored candidate and controlled P22b service remain unaccepted dependencies.
