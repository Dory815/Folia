# M3c — read-only custom Direct2D blend effect feasibility / ABI audit

Status: **audit only; no API frozen, implementation or acceptance**. `build/m3b-initial-warp.log` reports 24 pixel mismatches: six distinct test cases repeated at 96/120/144/192 DPI (Hue case 149; Color cases 169, 172, 173, 179; Luminosity case 190). Saturation has no mismatch in that log, but it shares the same nonseparable source helpers and must be covered. The existing M3b code remains pending. The aim considered here is a native GPU effect reproducing pinned tiny-skia's current math, including its unusual `clip_color` condition. CPU rasterization, SVG routing, and new scene APIs are outside this audit.

## Source math that must be matched

`highp.rs:506–616` operates on **premultiplied** f32 source `(r,g,b,a)` and destination `(dr,dg,db,da)` lanes, followed by `out.rgb = source.rgb*(1-da) + dest.rgb*(1-a) + adjusted.rgb`, `out.a = a + da - a*da`. The input images are 8-bit premultiplied colors loaded channelwise as `u8 as f32 * (1/255)` (`1245–1281`); output is clamped to [0,1], multiplied by 255 and rounded to integer (`1295–1345`). A shader must not silently switch to straight-alpha HSL/HSV, linear-light coefficients, or built-in D2D nonseparable blending.

| Source kernel | Exact selected adjusted-color sequence before common source-over terms |
| --- | --- |
| Hue `hue_k` 525–549 | Start `(r*a,g*a,b*a)` **not** `(r*da,...)`; `set_sat(..., sat(dr,dg,db)*a)`; `set_lum(..., lum(dr,dg,db)*a)`; `clip_color(..., a*da)`. |
| Saturation `saturation_k` 554–572 | Start `(dr*a,dg*a,db*a)`; set saturation to `sat(r,g,b)*da`; set luminosity to `lum(dr,dg,db)*a` (source comment explicitly says this is not redundant); clip with `a*da`. |
| Color `color_k` 577–594 | Start `(r*da,g*da,b*da)`; set luminosity to `lum(dr,dg,db)*a`; clip with `a*da`. |
| Luminosity `luminosity_k` 599–616 | Start `(dr*a,dg*a,db*a)`; set luminosity to `lum(r,g,b)*da`; clip with `a*da`. |

`lum` is `0.30*r + 0.59*g + 0.11*b`; `sat` is max channel minus min (`619–627`). `set_sat` captures original min/max/sat, maps min to zero and max to target saturation, with a selected zero result when sat equals zero (`629–642`). `set_lum` adds one common `target - lum(current)` delta to all channels (`644–649`). In `clip_color` (`652–670`), **the first branch tests `mx >= 0`, not `mn < 0`**. Root corrected this audit's original reversed interpretation of mask.blend: when mx is nonnegative, the first selection retains c; only otherwise does it choose `l + (c-l)*l/(l-mn)`. Then, if captured `mx > a`, it becomes `l + (c-l)*(a-l)/(mx-l)`; finally each channel is floored at zero. `mn`, `mx`, and `l` are captured before any channel mutation. This condition appears counterintuitive but is the pinned Source and is appearance-significant; replacing it with a specification formula is not parity. NaN/zero-denominator behavior, comparison selection and operation order need direct WARP probes. HLSL compiler contraction/reassociation and `min/max` behavior make bit-for-bit f32 agreement **unproven** by an ABI feasibility review.

## Windows 0.61.3 ABI path and private boundary suggestion

The generated bindings expose `ID2D1EffectImpl_Impl` with `Initialize`, `PrepareForRender`, `SetGraph` (`Direct2D/mod.rs:7368–7422`), and `ID2D1DrawTransform_Impl : ID2D1Transform_Impl : ID2D1TransformNode_Impl` with `SetDrawInfo`, three rectangle mappings and `GetInputCount` (`6514–6553`, `14069–14130`, `14289–14317`). The factory callback type is an `unsafe extern "system" fn(OutRef<IUnknown>) -> HRESULT` (`14478`). `ID2D1Factory1::RegisterEffectFromString` accepts a CLSID, UTF-16 metadata XML, optional `D2D1_PROPERTY_BINDING` slice and factory callback (`7878–7888`, binding struct `1603–1608`). The registered effect is then creatable through `ID2D1DeviceContext::CreateEffect` (`4865`). `windows_core::implement` and the generated `_Impl` traits make a Rust COM implementation plausible, but the exact multi-interface macro layout, `QueryInterface`, ownership and callback construction require a small **separately authorized compile/ABI proof** before design freeze; this audit did not compile one.

A narrow private backend entry point could be `custom_nonseparable_blend(context, background: &ID2D1Image, foreground: &ID2D1Image, mode: BlendMode, location: &str) -> Result<ID2D1Image, NativeRenderError>`. It would accept only Hue/Saturation/Color/Luminosity and leave the other twelve source modes on the existing M3b path. Four private CLSIDs/factory callbacks, each with exactly two inputs and a fixed kernel, appear simpler than a public mode property/binding; alternatively one CLSID with a bound mode property and a constant buffer is feasible. Root must choose and freeze that internal design. In either form, the effect input **0 is completed background/destination**, input **1 is foreground/source**, while HLSL variables use source `D2DGetInput(1)` and destination `D2DGetInput(0)`. No scene enum or public backend signature need change.

For a fixed two-input implementation, `Initialize` loads compiled shader bytes with `ID2D1EffectContext::LoadPixelShader` (`6862–6863`) and installs one draw-transform node through `ID2D1TransformGraph::SetSingleTransformNode` (`14141–14146`). The transform reports input count 2. `SetDrawInfo` selects the loaded shader GUID via `ID2D1DrawInfo::SetPixelShader` (`6439–6440`) and, if mode is a constant, uploads a correctly packed buffer (`6427–6428`). `PrepareForRender` updates constants when needed; `SetGraph` can reject variable graph changes for a fixed-input effect as the [custom effect guide](https://learn.microsoft.com/en-us/windows/win32/direct2d/custom-effects) describes. The output `ID2D1Image` and input image references must keep the effect graph alive until recorded use completes; do not unregister per draw or retain a borrowed `ID2D1DrawInfo` beyond the COM object's lifetime. Registration is per **factory instance**, not process-global; the current renderer holds `ID2D1Factory`, so it must cast/query `ID2D1Factory1` and coordinate one-time registration by actual COM factory identity, across renderer instances and threads. Device loss, new factories, duplicate registration and teardown each require an explicit error/lifetime path; nothing in the current M3b helper does this.

Microsoft requires defining `D2D_INPUT_COUNT 2`, `D2D_INPUT0_SIMPLE`, `D2D_INPUT1_SIMPLE` before `d2d1effecthelpers.hlsli`; then `D2D_PS_ENTRY` and `D2DGetInput(0/1)` read matching input pixels ([helpers](https://learn.microsoft.com/en-us/windows/win32/direct2d/hlsl-helpers), [D2DGetInput](https://learn.microsoft.com/en-us/windows/win32/direct2d/d2dgetinput), [entry point](https://learn.microsoft.com/en-us/windows/win32/direct2d/d2d-ps-entry)). This is preferable to hand-written normalized texture coordinates, since Direct2D may render cropped/offset input tiles. The transform should map both output rectangles to the corresponding same-pixel input rectangles; `MapInputRectsToOutputRect` must conservatively use the **union** of input bounds, not intersection, because one image may paint outside the other. It can return an empty opaque subrect conservatively, and `MapInvalidRect` must account for invalidation from either input. Out-of-bounds input samples need transparent black, consistent with Microsoft's custom-effect mapping rules. Treat `D2D1_PIXEL_OPTIONS_TRIVIAL_SAMPLING` as an optimization only after its assumptions are proven; `D2D1_PIXEL_OPTIONS_NONE` is conservative. All HRESULTs from registration, shader load/select, mapping, graph setup, creation, and final `EndDraw` must flow into `NativeRenderError`, retaining cleanup failures as the current `record` path does.

`windows 0.61.3` has `D3DCompile` in `Win32/Graphics/Direct3D/Fxc/mod.rs:2–10`, linked to `d3dcompiler_47.dll`; the renderer manifest currently enables `Win32_Graphics_Direct3D` but **not** `Win32_Graphics_Direct3D_Fxc` (`Cargo.toml:67–78`). Adding that feature would be a later root-owned manifest change. The binding exposes strictness and optimization flags (`Fxc/mod.rs:231–253`). A build-time compiled and embedded shader byte array would avoid depending on `D3DCompile` at runtime, but needs an SDK HLSL include path, reproducible compilation, checked-in/licensed binary policy and shader model validation. Runtime `D3DCompile` avoids checked-in bytecode but adds DLL availability and compile-error handling. Neither option was exercised here. Shader GUID, effect CLSID, property XML, `D2D1DrawInfo` and transform graph are native resources, not scene resources.

## Precision, acceptance feasibility and license

The existing WARP mismatch is at fixed interior pixels across four DPI values, so a mode formula difference is a credible cause; the log alone does not rule out sampling, quantization or alpha-boundary effects. Exact pixel parity requires establishing input format and premultiplication at the custom shader boundary, 1:1 sample coordinates, sRGB versus linear handling, intermediate buffer precision, float arithmetic order, clipping and final 8-bit rounding. [Microsoft's precision guide](https://learn.microsoft.com/en-us/windows/win32/direct2d/precision-and-clipping-in-effect-graphs) explains that command-list inputs do not themselves specify a precision, and render-target/context/effect settings can determine intermediates. A 32bpc-float effect buffer may help preserve f32 math but does not automatically reproduce tiny-skia's 8-bit input load and output rounding. Native code should first probe raw source/destination samples and shader output against independent tiny-skia computations, then compare final WARP pixels for opaque/translucent and out-of-bounds cases, each of four modes, branch thresholds and all four DPI values. Do not relax Source expectations to make a shader pass. If WARP/HLSL cannot reproduce pinned output at the required byte tolerance, feasibility must be reported as failed rather than silently routing through CPU or SVG.
