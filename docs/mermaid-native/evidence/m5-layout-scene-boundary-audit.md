# M5: `Layout` to `DiagramScene` boundary audit

Read-only source audit for the Direct2D backend task. No production files, builds, tests, or gold data were changed. The architecture and scope correction in `architecture.md` govern this report: finish the shared scene compiler and parallel scene consumers; do not port tiny-skia raster internals.

## Existing route and exact boundary

- `src/lib.rs:224-228` implements the public `render_with_options`: parse -> `compute_layout` -> `render_svg`. `render_strict` at `:275-279` and timed SVG entry points at `:379` follow the same SVG endpoint. There is no public `Layout -> DiagramScene` function.
- `src/render.rs:85-87` delegates `render_svg` to `render_svg_with_dimensions`. `measure_svg_dimensions` at `:89-204` carries diagram-specific output sizing and viewBox policy. `render_svg_with_dimensions` at `:206-303` establishes state-font sizing, dimensions, link/XML attributes, max-width CSS and emits root SVG/background. Its content dispatch is `:314-318` for C4; `:384-454` for Error, Sankey, Architecture, Radar, Requirement, Pie, Quadrant, Gantt, XYChart, Timeline, Journey and GitGraph; the remaining generic path begins `:456` and contains shared subgraph/sequence/node/edge/label rendering.
- Output order is semantically visible and must become ordered scene nodes. After the background (`:305-312`), family early-return branches at `:314-454` emit their own complete content. In the generic branch, subgraphs run first (`:456-600`); sequence boxes and frame/lifeline/activation/note content follow (`:604-774`); sequence edges (with endpoint decorations and center/start/end labels) are drawn in the edge loop (`:777-1005`), then sequence numbering (`:1007-1025`). Non-sequence edges and their center/start/end label backgrounds/text are emitted by `:1027-1367`. Non-sequence nodes then follow in `:1369-1481`, sorted by descending area only for Treemap (`:1371-1381`), with each node body, divider lines and label contiguous; Sequence actor nodes/footboxes are emitted afterward in `:1483-1526` and `:1527+` respectively. The generic path closes the root SVG at `:1612-1614`; family-specific overlay details live inside the early-return helpers named below. SVG append order is the painter-order evidence.
- Dimensions are not simply `layout.width/height`: Error uses its `render_width/height` and viewBox; Requirement adds configured render padding; C4 uses its own viewBox and dimensions; GitGraph offsets its viewBox; Mindmap scans node bounds and applies padding; Sequence adds four asymmetric constants (`:80-83`, used at `:162-174`); others clamp natural dimensions to at least 1. Preferred aspect ratio and valid explicit dimensions are resolved in `measure_svg_dimensions:181-203`. SVG-only output policy (100% width/max-width styles for C4/GitGraph/Mindmap/Pie at `:246-289`) should stay in SVG serialization, while scene dimensions/viewBox/root mapping need one shared documented policy. `render_svg_with_dimensions` currently emits background as a full-viewBox rect using theme background (`:305-312`).
- Theme/options affect drawing throughout `render.rs`: font sizing (including State's 0.85 multiplier at `:213-217`), colors, label fills, borders, padding, marker form/style, and family configuration. They must be resolved into scene paint/text/geometry before backend dispatch, not re-derived by D2D.
- Text remains SVG-side emission today. `text_block_svg*` and related calls emit positioned lines/anchors and family-specific font/style semantics (many callsites throughout render.rs; representative generic sequence calls `:621-630`, `:663-681`, `:731-739`, state notes `:763-773`). Scene text types already model fonts, positioned glyph runs and appearances (`scene/text.rs:16-102`); the accepted `compile::text_presentation` and text helper modules capture source-facing presentation only. The complete shared text resolver/shaper/layout is not established by those request types. Scene compilation must finish text layout once and populate scene text; D2D owns native drawing/font services, SVG owns text serialization.
- Current Direct2D API `backends/direct2d.rs:116+` accepts only `&DiagramScene` (`record_scene`), consumes scene dimensions, viewport and ordered nodes, and has no Mermaid `Layout`/parser dependency. This is the intended downstream consumer boundary.

## Family coverage and missing scene compilation

The parser's `DiagramKind` enum (`src/ir.rs:12-36`) names all 23 supported families: Flowchart, Class, State, Sequence, ER, Pie, Mindmap, Journey, Timeline, Gantt, Requirement, GitGraph, C4, Sankey, Quadrant, ZenUML, Block, Packet, Kanban, Architecture, Radar, Treemap and XYChart. Layout consolidates many into `DiagramData::Graph` (`src/layout/types.rs:451-468`), so compiler dispatch must use both `layout.kind` and the data variant. C4, Sequence, Pie, Quadrant, Gantt, Sankey, GitGraph, XYChart, Timeline and Journey have dedicated data variants; Graph is shared by Flowchart/Class/State/ER/Requirement/Mindmap/ZenUML/Block/Packet/Kanban/Architecture/Radar/Treemap. Requirement is a Graph variant selected by the explicit kind branch at `render.rs:408-412`; Architecture and Radar likewise use Graph data but their explicit branches are at `:396-406`. Error layout is separately rendered and is not one of the 23 parser families.

The gap is the entire family-specific lowering now embedded in SVG emission, not a missing native primitive backend. `render_svg_with_dimensions` and its family helpers compute presentation geometry and styles as they append SVG: shape selection/rounding, edge path spelling and markers, label background/position, decorations, icon details, clipping/grouping, and family overlays. The scene compiler must transfer all these decisions to typed nodes and scene metadata. In particular, family-specific helpers called in the early-return branches (`render_c4`, `render_error`, `render_sankey`, `render_architecture`, `render_radar`, `render_requirement`, `render_pie`, `render_quadrant`, `render_gantt`, `render_xychart`, `render_timeline`, `render_journey`, `render_gitgraph`) remain SVG string producers today. The generic path holds Flowchart/Class/State/ER/Mindmap/ZenUML/Block/Packet/Kanban and shared graph behavior; these do not yet have a complete typed lowering either.

A parallel scene SVG consumer is also absent. Current SVG serialization reads `Layout` directly and embeds SVG-specific concerns (XML metadata/links, marker definitions/references, attributes, max-width CSS and viewBox text) as it draws. A scene SVG serializer must consume only the completed scene, preserving scene order and supported export metadata, with no second layout or geometry calculation. The existing renderer cannot serve as a compliant consumer by reparsing an intermediate SVG or by continuing to read `Layout` independently after the scene exists.

## Existing helpers reusable by a compiler

The following accepted typed helpers are directly reusable where their signatures and exact behavior fit; they are leaf geometry/presentation conversions, not a family compiler:

- `scene/compile/paths.rs`: `dedupe_points`, `points_to_path`, `rounded_polyline_path`, `basis_curve_path` for path geometry.
- `scene/compile/edge_symbols.rs`: `arrowhead`, `edge_decoration` for typed endpoint glyphs/decorations.
- `scene/compile/node_shapes.rs`: `node_shape` for typed ordinary node geometry/style.
- `scene/compile/text_helpers.rs`: normalized family/line helpers and text presentation requests (`text_block`, anchor/font-size/weight variants, `text_line`, `c4_text`). Reuse only as source request preparation; do not mistake it for completed shared shaping.
- `scene/compile/edge_label_geometry.rs`: label background visibility and segment/rectangle distance/intersection predicates.
- `scene/compile/architecture_icons.rs`: typed architecture icon geometry.
- `scene/compile/c4_style.rs`: C4 shape color/font selectors.
- `scene/compile/sankey_labels.rs`: Sankey numeric label formatting.
- `scene/compile/er_attributes.rs`: ER attribute line parsing.

The common scene vocabulary is already present: `SceneBuilder` (`scene/builder.rs:11-52`) owns ordered nodes/resources and publishes only after `finish`; `DiagramScene` (`scene/mod.rs:91-114`) provides read-only dimensions, viewport, nodes, gradients/fonts/images and metadata; `ShapeGeometry`, `Path`, `GroupNode`, transforms/clips, paint/stroke/blend, text/image nodes and export metadata are typed in `scene/{geometry,paint,text,mod}.rs`. These definitions support a compiler without adding a raster engine. Whether every SVG feature has an adequate scene representation must still be checked as lowering proceeds; unsupported commands cannot be silently discarded.

## Minimal concrete file responsibilities and interfaces

The current renderer can serve as an independent reference while the scene route is developed. The final normal backend route must use one completed scene, without an old/new compatibility fallback. Root owns final names/interfaces; this is a concrete proposal based on current module structure:

- `src/scene/compile/mod.rs` plus focused family modules: expose a single `compile_layout(layout: &Layout, theme: &Theme, config: &LayoutConfig, dimensions: Option<(f32,f32)>, text: &mut dyn TextResolver) -> Result<DiagramScene, SceneError>` (or a compiler context owning that resolver). The resolver/provider is explicit because `DiagramScene` text requires font resources and positioned glyph runs, while a portable compiler cannot create platform font services itself. The compiler dispatches on kind/data, computes completed family placement and dimensions, resolves styles, requests shared text resolution/shaping through this boundary, and pushes nodes in source renderer order. Keep accepted leaf helpers in their current modules; no per-backend layout.
- `src/backends/svg.rs` (or a scene serializer module adjacent to `backends`): expose `render_scene_svg(scene: &DiagramScene) -> Result<String, ...>` and serialize typed nodes/resources/metadata in order. It does not accept Layout, Theme, or LayoutConfig and does not re-layout.
- `src/backends/direct2d.rs`: retain current `record_scene(&DiagramScene)` and native resource/render lifecycle; it does not accept Mermaid input and does not serialize or parse SVG.
- `src/lib.rs`: keep parse/layout public stages; add a shared scene-render entry (for backend API/acceptance) and route ordinary SVG public APIs through `compile_layout -> render_scene_svg`. Folia may call the native scene route only after Root's full backend acceptance; do not wire it during this audit.

The returned scene should contain final dimensions and viewBox/root viewport transform, theme-resolved background and every visible ordered draw command, text runs resolved through the explicit text service, clips/transforms, marker geometry, styles, and export metadata/resources required by SVG. Both consumers then operate over the same immutable value.
