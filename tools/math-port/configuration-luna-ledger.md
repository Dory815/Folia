## Current native boundaries

- `Context::construct` now exists as a narrow native-allocation entry point. Runtime metadata uses observed CJS function length and call behavior; constructor callbacks bind and initialize the canonical Context identity.
- Configuration and ParserConfiguration Context identities are the sole owners of their source-visible fields. Native methods resolve current field values, including after public property replacement. ParserConfiguration's native list carriers do not yet expose all Source prototype methods to Context callers; `append` is not currently installed on the Context prototype, and FunctionList/PrioritizedList carrier method replacement is not observable through those fields.
- `ConfigurationHandler.initializeModule` installs its exported ordinary Context object and routes its methods to the single registry; `keys()` returns a live Map iterator with inherited `next` and `Symbol.iterator`. The current registry models enabled package string names and real Configuration values; arbitrary Map key/value domains remain unsupported rather than being stringified or copied. `getPackage` still needs a follow-up to resolve the live exported `ConfigurationHandler.get` property instead of calling the native registry directly.
- The actual emitted Configuration constructor body applies defaults and handler merge, and its observed function length is 13. Context::construct provides the distinct native allocation entry point, and constructor metadata follows observed CJS call behavior.
- Priority conversion now uses the canonical `Context::toNumber` bridge for native primitive values; arbitrary object-to-primitive behavior remains an explicit unsupported boundary.
- `Configuration.add` requires actual native StackItem class identities and a TeX identity. Those identity entries are created by their owning class/runtime setup; configurations with unbound class objects fail at that boundary rather than being replaced with fake factories.
- `Configuration.config` function bodies receive the canonical ParserConfiguration native identity, but the TeX callback argument currently crosses as `TeX*`; a shared TeX callable argument adapter is still needed for callbacks that require `TeXRef`.
- Runtime class metadata for TeX, ParseOptions, TexParser, and KeyValueDef/KeyValueTypes is not installed by this file. Those are real peer owners, so the runtime explicitly lists missing constructors. ColumnParser's constructor identity is installed, but its Context prototype method bindings still need the canonical peer argument identities.
- Configuration packages and parser names use the string-key registry and ordinary Context arrays. Context iterator dispatch supports dynamic package iterables; registry non-string key semantics remain outside the enabled package domain.
- The third combined gate compiled the parser library and linked `FoliaMathHostTests`. Iterator host assertions passed; Array host assertions exposed an unsequenced trace read in the candidate fixture. That fixture now evaluates each operation before collecting its trace and is awaiting Root's rerun. This is not a complete parser/core parity claim.
